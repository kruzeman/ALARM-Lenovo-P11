# Звук

Карта: `Lenovo-TB-J606F` (компонент `snd-soc-sm8250`, драйвер `qrb4210-rb2-sndcard`).

```
/proc/asound/cards
 0 [LenovoTBJ606F]: sm4250 - Lenovo-TB-J606F
```

## Что уже работает

- **Динамики** — 4 усилителя AW88258 на I²C0 (`0x34–0x37`) на `PRIMARY_TDM_RX_0`, 48 кГц / 4 слота × 32 бита,
  стерео в слотах 0/1. UCM-профиль включает маршрут
  `name='PRIMARY_TDM_RX_0 Audio Mixer MultiMedia1'` и ставит громкость усилителей.
- **Гарнитура/разъём** — WCD937x, SoundWire (rx/tx/va macro) и `pm4125` поднимаются, MBHC видит джек,
  но аналоговый выход идёт через **FSA4480** (USB-C), который пока не описан — звука в разъёме нет.
- **Микрофоны ES7210** — драйвер кодека есть и работает до момента запуска потока, см. ниже.

WirePlumber: этому TDM-тракту нужен **S16LE**, иначе цифровая тишина.
`/etc/wireplumber/wireplumber.conf.d/51-j606f-nommap.conf`:

```
monitor.alsa.rules = [ { matches = [ { node.name = "~alsa_output.*" } ]
  actions = { update-props = { audio.format = "S16LE", api.alsa.period-size = 1024, api.alsa.headroom = 4096 } } } ]
```

## Микрофоны ES7210 (в работе)

Кодек — Everest ES7210 (4-канальный АЦП) на I²C1 `0x40`, данные — в primary TDM (та же шина, что у
динамиков). Драйвер `sound/soc/codecs/es7210.c` (патч 0003) инициализирует чип и регистрируется в карте:

```
/sys/kernel/debug/asoc/Lenovo-TB-J606F/es7210.1-0040
```

Линк в DTB (патч 0001): `builtin-mic-dai-link` → `cpu = <&q6afedai PRIMARY_TDM_TX_0>`.

### Что уже выяснено (важно для продолжения)

1. Для TDM-порта **обязателен дочерний узел `&q6afedai`** с параметрами синхронизации:

   ```dts
   dai@19 {
           reg = <PRIMARY_TDM_TX_0>;
           qcom,tdm-sync-mode = <0>;
           qcom,tdm-sync-src  = <1>;
           qcom,tdm-data-out  = <0>;
           qcom,tdm-invert-sync = <1>;
           qcom,tdm-data-delay = <0>;
           qcom,tdm-data-align = <0>;
   };
   ```

   Без него `q6afe_tdm_cfg` нулевой: раньше это давало SMMU fault в аудио-IOMMU и падение ADSP
   (цикл перезагрузок), теперь — чистую ошибку `-22`.
2. Машинный драйвер (`sm8250.c`, патч 0002) на `PRIMARY_TDM_TX_0` ставит `IBIT`-клок, `set_tdm_slot()`
   и `set_channel_map()` — по аналогии с рабочим RX-путём динамиков.
3. **Остаётся блокер**: `AFE_PORT_CMD_DEVICE_START` для порта `0x9001` отбивается прошивкой ADSP —
   `DSP returned error[2]`, `AFE enable for port 0x9001 failed -22`. Перебраны:
   2 и 4 канала, маски слотов `0x3` и `0xF`, с картой каналов и без, одинаковые sync/clock с RX.

Что проверять дальше:

- таблицу AFE-портов в стоковой прошивке ADSP (какие TX-порты она вообще объявляет);
- не висят ли микрофоны на второй LPASS-шине: в стоковом DTB есть отдельная группа пинов
  `lpi_i2s2_*` помимо `lpass-tdm1-*`, которые использует динамики. Если АЦП на I2S2, поднимать надо
  порт `*_MI2S_TX`, а не TDM;
- порядок загрузки модулей: `q6afe` создаёт тактовый провайдер `q6afecc`, без которого LPASS-pinctrl
  висит в deferred, а вместе с ним и вся карта:

  ```bash
  modprobe q6afe q6core q6routing q6asm q6afe-dai q6asm-dai
  modprobe pinctrl-sm6115-lpass-lpi
  modprobe snd_soc_sm8250
  ```

### Как тестировать

`rootfs/usr/local/bin/mic-test.sh` включает маршрут, пишет 3 секунды с `hw:0,1` и `hw:0,0`,
считает пик и складывает всё в `/var/log/mic-test.log` (лог переживает падение):

```bash
amixer -c0 cset name='MultiMedia2 Mixer PRIMARY_TDM_TX_0' 1
arecord -D hw:0,1 -f S16_LE -c 2 -r 48000 -d 3 /tmp/mic.wav
```

Если в `dmesg` появляется `AFE enable for port 0x9001 failed -22` — порт не запущен, запись не пойдёт
(файл не создаётся).

### Текущее состояние встроенных микрофонов (ES7210 на PRIMARY_TDM_TX_0)

Захват теперь **открывается** — DSP принимает порт. Для этого понадобилось два условия:

1. **Двухканальный TDM-кадр.** `snd_soc_dai_set_tdm_slot(cpu, GENMASK(1,0), 0, 4, 32)` — с
   четырёхканальной маской (`GENMASK(3,0)`) ADSP отвечает `ADSP_EBADPARAM` (ошибка 2) на
   `AFE_PORT_CMD_SETUP`, и порт не стартует.
2. **Коэффициент кодека должен соответствовать кадру, а не разрядности сэмпла.** Кадр TDM —
   `slots × slot_width` = 4 × 32 = 128 бит, поэтому ES7210 нужен `REG02 = 0xC1` (128 × fs).
   `0x41` (64 × fs) верен только для I2S-кадра 2 × 32. Теперь `es7210.c` принимает
   `set_tdm_slot` от машины и считает коэффициент из него.

Что пока не закрыто: файл записи создаётся (144000 кадров, стерео, 3 с), но сэмплы **нулевые** —
порт работает, а кодек данных не отдаёт. Прочитать регистры ES7210 из userspace нельзя (адрес
0x40 занят драйвером), поэтому дальше: доступ через `i2c-dev` из драйвера или debugfs, проверка
что кодек реально получил TDM-инициализацию (`0x11/0x12`, `0x02`), какой MCLK/SCLK он видит и на
какой из двух линий данных LPASS TDM (`gpio8`/`gpio9`) АЦП выводит `SDOUT`.

Предупреждение из той же сессии: стоковые карты protection-domain `adspr/adsps/adspua.jsn`
**нельзя** копировать в `/lib/firmware/qcom/sm6115/LENOVO/J606F/` — с ними ADSP уходит в цикл
`qcom_q6v5_pas ... Handover signaled`, и пропадает Wi-Fi (его прошивка грузится через ADSP).
Для звука `pd-mapper` на этом устройстве не нужен.


### Карта, которая появлялась не в каждую загрузку (гонка PDR) — исправлено

У `q6core`/`q6afe`/`q6asm`/`q6adm` в `sm6115.dtsi` стояло
`qcom,protection-domain = "avs/audio", "msm/adsp/audio_pd"`. `apr_probe()` регистрирует такие
сервисы только после того, как PDR сообщит о подъёме домена, а сообщение приходит по QRTR от
ADSP — канал `IPCRTR` объявляется не в каждой загрузке (у CDSP он есть, у ADSP — не всегда).
Когда его не было, не создавался `service@4`, не регистрировался `q6afecc`, LPASS-пинконтроллер
оставался в `devices_deferred`, и карта не появлялась: `--- no soundcards ---` и ни одной
ошибки ASoC в журнале.

`kernel/patches/0006-dts-audio-apr-no-protection-domain.patch` убирает это свойство у четырёх
аудио-сервисов — они регистрируются безусловно в `apr_probe()`. После патча в каждой загрузке
`service@` × 4, `devices_deferred` пуст, карта на месте.

### TDM TX: параметры, которые mainline не передавал

`q6afe_tdm_port_prepare()` не копировал `ctrl_data_out_enable`, `ctrl_invert_sync_pulse` и
`ctrl_sync_data_delay` в конфиг AFE-порта, хотя парсер DT уже читал `qcom,tdm-data-out`,
`qcom,tdm-invert-sync` и `qcom,tdm-data-delay`.
`kernel/patches/0005-q6afe-tdm-tx-data-out.patch` передаёт их, а TX-dai выставляет
`qcom,tdm-data-out = <1>`.

Состояние после всего этого: ES7210 по I²C настроен как 16-бит TDM I2S
(`0x11 = 0x60`, `0x12 = 0x02`, `0x08 = 0x14`), чип рапортует `CSM_STATE = normal`, аналог включён,
микрофоны выбраны (`0x43` бит 4), AFE-порт стартует, `arecord` пишет файл полного размера — но
все сэмплы по-прежнему нулевые. Дальше по порядку: полярность `qcom,tdm-invert-sync` на TX-узле
и на какой линии LPASS сидит выход АЦП (`gpio8` или `gpio9`), то есть не нужен ли порт
`PRIMARY_TDM_TX_1`.


### Микрофоны не на TDM — они на SoundWire-входах кодека

Стоковый `mixer_paths.xml` (найден сканированием `/dev/sda14` по `<mixer>`) закрывает вопрос:

```
<path name="spkr-vi-record">
    <ctl name="PRI_TDM_RX_VI_FB_MUX" value="PRI_TDM_TX_0" />
    <ctl name="PRI_TDM_TX_0 Channels"  value="Four" />
    <ctl name="PRI_TDM_TX_0 Format"    value="S32_LE" />
    <ctl name="PRI_TDM_TX_0 SampleRate" value="KHZ_48" />
</path>
<path name="amic2">
    <ctl name="TX DEC0 MUX"   value="SWR_MIC" />
    <ctl name="TX SMIC MUX0"  value="SWR_MIC4" />
    <ctl name="TX_CDC_DMA_TX_4 Channels" value="One" />
    <ctl name="TX_AIF2_CAP Mixer DEC0" value="1" />
</path>
```

`PRI_TDM_TX_0` в четырёхканальном `S32_LE` — это `spkr-vi-record`: обратная связь
смарт-усилителей (VI-сенс для защиты динамика). Источник этого TX-потока — сами усилители,
поэтому захват со стороны ES7210 физически не мог дать ничего, кроме нулей. Мы это и
измерили во всех вариантах: 2/4 слота, TDM-DSP и TDM-I2S, обе полярности sync, `TX_0` и
`TX_1`, 16 и 32 бита, передача `ctrl_data_out_enable` в DSP.

Встроенные микрофоны — это `amic2`/`amic3` → `TX DEC0 MUX = SWR_MIC`,
`TX SMIC MUX0 = SWR_MIC4` → `TX_CDC_DMA_TX_4`, то есть микрофонные входы кодека
**WCD9370** по SoundWire. Чтобы получить захват, нужно поднимать тракт WCD937x
(SoundWire → кодек → CDC_DMA_TX), а не дальше крутить TDM.

ES7210 остаётся подключённым и рабочим как второй вход, но на этой плате Android
использует для встроенных микрофонов не его.


### Где на самом деле живут встроенные микрофоны (измерено 2026-11-08)

Работа с ES7210/TDM гонялась за неверной шиной. Стоковый `mixer_paths.xml` это доказывает:

```
<path name="spkr-vi-record">
    PRI_TDM_RX_VI_FB_MUX = PRI_TDM_TX_0   ← обратная связь смарт-усилителей
<path name="amic2">
    TX DEC0 MUX = SWR_MIC, TX SMIC MUX0 = SWR_MIC4, TX_CDC_DMA_TX_4 Channels = One
```

`PRI_TDM_TX_0` в режиме `Four`/`S32_LE` — это усилители, рассказывающие о себе для защиты
динамика: источник там сами усилители, поэтому захват со стороны АЦП физически не мог дать
ничего, кроме нулей. Мы это и измерили во всех вариантах (2/4 слота, TDM-DSP и TDM-I2S, обе
полярности sync, `TX_0` и `TX_1`, 16 и 32 бита, передача `ctrl_data_out_enable` в DSP).

Микрофоны — это `amic2`/`amic3`: АЦП кодека **WCD9370**, который приходит в AP по SoundWire
(на bengal шиной `tx_swr` владеет `va_swr_master`, LPI gpio0-2), а затем через CDC DMA TX.

### Состояние SoundWire TX и два найденных фикса

* Оба слейва кодека привязаны (`sdw:2:0:0217:010a:00:4` RX, `sdw:3:0:0217:010a:00:3` TX), но
  TX-слейв висит в `Alert` вместо `Attached`, а захват падает с `hw_ptr = 0` и
  `Input/output error` на любом порту (`TX_CODEC_DMA_TX_3/4`, 1 и 2 канала, 8 и 48 кГц).
* В узлах не было статических маппингов каналов, драйвер писал
  `Static channel mapping not specified using device channel maps`. Добавление
  `qcom,tx-channel-mapping = /bits/ 8 <1 2 1 1 2 3 3 4 1 2 3 4>` и
  `qcom,rx-channel-mapping = /bits/ 8 <1 2 1 1 2 1 1 2>` (взяты с референсной платы)
  убирает предупреждение.
* Линк с VA-макро (`<&vamacro 0>` + `VA_CODEC_DMA_TX_0`) отправляет устройство в
  Qualcomm CrashDump ещё на загрузке: ADSP падает до открытия потока, поэтому этот путь
  закрыт, пока шина нездорова.
* Лог краша (побит ECC, но читается): `arm-smmu c600000.iommu: Unhandled context fault:
  fsr=0x402, SID=0xE3` сразу после попыток захвата. Воспроизведение не падает никогда.

### Дальнейшие шаги (по порядку)

1. Вывести TX-слейв из `Alert`: сравнить конфигурацию портов мастера на `a740000`
   (`din-ports = 3`, а контроллер рапортует 4) с вендорскими значениями и проверить, что
   VA-макро действительно тактируется (в его узле нет `qcom,dmic-sample-rate`, вендор ставит
   `qcom,va-dmic-sample-rate = <600000>`).
2. Только после этого менять DAPM-маршрут под стоковый выбор мукса: `TX SMIC MUX0 = SWR_MIC4`
   означает, что выход кодека должен идти в `TX SWR_INPUT4`, а не в `TX SWR_INPUT1`.
3. Затем направить линк захвата на нужный порт CDC DMA TX и проверить через `arecord`.

### Состояние на конец 8 ноября (микрофоны)

Аппаратно на верхней грани два отверстия — минимум два микрофона, то есть целевой
режим захвата: два канала (кодек DEC0 и DEC1, входы SWR_MIC0 и SWR_MIC4).

Что сделано и проверено:
- TX-шина SoundWire поднята до рабочей конфигурации: `qcom,tx-port-mapping = <1 2 3 4>`
  (ADC1..4 → порты 1..4), `qcom,tx-channel-mapping` по вендорской таблице,
  `qcom,din-ports = <4>`; маршруты ADC1..3 → `TX SWR_INPUT0/1/2/4/5`.
- Найдена причина `Bus clash detected` и вечного `Alert`: драйвер включал **девять**
  каналов на четырёх портах (все каналы кодека по умолчанию включены). После гашения
  лишних свитчей (`ADC1/3`, `DMIC0..5`, `MBHC Switch`) поток стал минимальным:
  `active_ports=1`, `ch_mask=0x1`, `ch_count=2` — конфликт ушёл.
- Линк захвата переведён на `TX_CODEC_DMA_TX_4`, как `amic2` в стоке.

Остаток: захват по-прежнему завершается `EIO` на первом чтении, DSP не отдаёт буферы.
`hw_params`, prepare и старт порта проходят без ошибок, лог ядра пуст даже с dyndbg по
`soundwire`, `wcd937x`, `q6asm`. Следующий шаг — разбирать связку ASM-сессии с
AFE-портом на стороне ADSP, а не конфигурацию шины.

### Захват со встроенных микрофонов: текущее состояние (WCD9370 по SoundWire)

Возможен ли захват вообще, решает DT, и грузить надо образ, собранный из дерева, а не из старого дампа.
С DTB из дерева (`sm6115p-lenovo-j606f-hx83102p.dtb`) изменились сразу три вещи:

- у built-in микрофона настоящая цепочка `codec { sound-dai = <&wcd937x 1>, <&swr0 0>, <&vamacro 0> }`,
  `cpu { sound-dai = <&q6afedai VA_CODEC_DMA_TX_0> }` — в старом образе эта же ссылка указывала на ES7210
  (`<&es7210>`), поэтому бэкенд `VA_CODEC_DMA_TX_0` не находился и захват падал уже на `open()` с `EINVAL` /
  `no BE found for VA_CODEC_DMA_TX_0 Capture`;
- у TX-мастера SoundWire `qcom,din-ports = <4>` и таблицы `qcom,ports-*` на 4 записи — иначе
  `din-ports (3) mismatch with controller (4)`;
- у слейва кодека `qcom,tx-port-mapping = <1 2 3 4>` и 12-байтный `qcom,tx-channel-mapping`.

С таким образом **оба слейва SoundWire в состоянии `Attached`** (TX раньше висел в `Alert`, и одного этого
хватало для `EIO`/нулей), карта регистрируется без ошибок маршрутов, и захват больше не отказывается
открываться.

Что осталось: `arecord -D hw:0,1` стартует и **блокируется в ядре** (`arecord` в состоянии `D`, открытый PCM
остаётся `OPEN` с мёртвым владельцем) — поток идёт, но DSP не отдаёт буферы TX. Заблокированный захват без
перезагрузки не снять, а каждая перезагрузка сейчас стоит минут: `j606f-wifi-reprobe` удалён во время разбора
CFI-падений.

Порядок дальнейших шагов: вернуть `j606f-wifi-reprobe`; гонять захват **неблокирующе** (`arecord -N`), чтобы
ядро не вставало; прочитать инструментированный `dev_info` в `wcd937x_sdw_hw_params()` — настраивается ли
кодек вообще и с какими портами/каналами; затем смотреть сторону AFE/q6asm, которая должна отдавать буферы TX.

### Эксперимент: какой CDC-DMA backend у встроенного микрофона

Проверены два варианта DT:

- `cpu { sound-dai = <&q6afedai VA_CODEC_DMA_TX_0> }` (VA-путь, как в стоковом микшере): оба слейва
  SoundWire в `Attached`, захват открывается без `EINVAL`/`EBUSY`, но первый же `arecord` **вешает задачу в
  `D`**, открытый PCM остаётся `OPEN` с мёртвым владельцем; после этого кодек может не
  переинициализироваться (`wcd9370-codec ... Initialization not complete`, `ASoC error (-110)`) и карта
  исчезает до сброса питания.
- `cpu { sound-dai = <&q6afedai TX_CODEC_DMA_TX_3> }` (backend из референса qcm6490-idp, уникальный DAI —
  `TX_CODEC_DMA_TX_4` уже занят микрофоном гарнитуры, а дважды его использовать нельзя: карта не
  регистрируется и устройство уходит в fastboot): TX-слейв SoundWire остаётся в **`Alert`**.

То есть VA-путь проходит дальше по шине (attached, поток открывается), но вешает ядро, а TX-макрос не
цепляется даже до `Attached`. Следующая диагностика не требует живой консоли: дать захвату повиснуть,
сделать сброс питания и прочитать `journalctl -k -b -1 | tail -60` — journald пишет сообщения ядра на диск,
поэтому последние строки перед зависанием (включая инструментированный `dev_info` из `hw_params`) доживают.

### Рабочая конфигурация: встроенные микрофоны

Тракт захвата: АЦП кодека (ADC2 <- AMIC2) -> порт 2 TX-слейва SoundWire -> шина `swr0` (`a740000`, её
тактирует TX-макрос) -> `TX SWR_INPUT1` -> `TX SMIC MUX0` (`SWR_MIC1`) -> `TX DEC0 MUX` (`SWR_MIC`) ->
`TX_AIF1_CAP Mixer DEC0` -> CDC DMA TX3 -> DSP (`TX_CODEC_DMA_TX_3`).

Тракт не работал из-за двух ошибок:

1. В DAI-линке стоял `&vamacro`. VA-макрос обслуживает голосовую активацию, а шину TX тактирует `&txmacro`,
   и данные АЦП кодека идут через него. С VA-макросом карта регистрировалась и поток SoundWire даже
   готовился, но в DSP не приходило ни одного сэмпла.
2. Три mux-а TX-макроса (`TX SMIC MUX0`, `TX DEC0 MUX`, `TX_AIF1_CAP Mixer DEC0`) по умолчанию выключены.
   Пока выключен `TX_AIF1_CAP Mixer DEC0`, `q6asm_read()` для каждого периода возвращает 0, но событие
   `DATA_READ_DONE` не приходит, и `snd_pcm_lib_read` сдаётся через ~0,7 с с `-EIO` («capture read timeout»).

Имена виджетов важны: у нас `lpass_ver_10_sm6115`, то есть набор `tx_macro_dapm_widgets_v9_2`, где входы
называются `TX SWR_INPUT0..7`. В более новых наборах (sm8250/sm8450) те же входы зовутся `TX SWR_ADCn`;
с чужими именами карта не собирается: `ASoC: Failed to add route`.

Патчей ядра для этого не нужно — рабочая конфигурация собирается только из DTS и UCM. (Опыты с
`VA_CODEC_DMA_TX_0`, где всплывал NULL-deref в `sdw_stream_add_slave()`, — тупиковая ветка:
`VA_CODEC_DMA_TX_0` отсутствует в `qcom_snd_is_sdw_dai()`, поэтому `qcom_snd_sdw_startup()` выходил до
установки потока.)

В `rootfs/usr/share/alsa/ucm2/Lenovo/TB-J606F/HiFi.conf` добавлено устройство `Mic` с
`CapturePCM "hw:${CardId},1"` и `EnableSequence`, которая выставляет `MultiMedia2 Mixer TX_CODEC_DMA_TX_3`,
`ADC2 MUX`, `TX SMIC MUX0`, `TX DEC0 MUX` и `TX_AIF1_CAP Mixer DEC0`. После этого PipeWire сразу после
загрузки показывает источник «Built-in microphones», а `pw-record --rate 48000 --channels 1 --format s16`
отдаёт живой сигнал (замер: пик 32768 с редкими выбросами, RMS ~3,8 тыс. на шуме комнаты при единичном
усилении).

**Известное ограничение: каждый захват даёт всего ~0,5 с звука, дальше цифровая тишина.** Это не проблема
«переоткрытия» — воспроизводится уже в первом же потоке. Что измерено:

- RMS по 0,5 с на пятисекундной записи: `[711, 15, 0, 0, 0, …]` — один короткий всплеск, дальше точные нули
  (именно цифровая тишина, а не тихая комната).
- DSP при этом продолжает отдавать буферы: событие `ASM_CLIENT_EVENT_DATA_READ_DONE` приходит непрерывно
  (509 событий за 5 с, счётчик растёт с #14 до #526, состояние потока RUNNING). То есть DSP отдаёт буферы, но
  они заполнены нулями — значит обрыв выше по тракту (кодек → SoundWire → TX-макрос).
- В момент тишины TX-макрос по-прежнему тактируется (`LPASS_CLK_ID_TX_CORE_MCLK` 19,2 МГц и `lpass-tx-mclk`
  9,6 МГц, оба `Y`), слейв и мастер в состоянии `active`.
- Дамп регистров кодека, снятый дважды внутри одного потока (в начале, когда звук идёт, и позже, в тишине):
  меняется только `0x3125` (`0x0a → 0x08`) — это `WCD937X_MBHC_NEW_FSM_STATUS`, автомат детектора гарнитуры.
  Дамп регистров TX-макроса не меняется вообще. Выключение `MBHC Switch` перед записью не помогает, так что
  детектор гарнитуры — ложный след.
- Последовательность запуска SoundWire эталонная: `port_params(bank1)` → переключение банка → `prep(bank0)` →
  `port_params(bank0)` → `chn_en en=1 addr=0x220 ch_mask=0x1` → переключение банка. Teardown зеркален и
  выключает канал в обоих банках. Ни в рабочем, ни в тихом потоке эта последовательность не отличается.

Куда смотреть дальше: обрыв между АЦП/TX-портом кодека и тем, что вычитывает мастер. TX-порт кодека остаётся
включённым, карта регистров не меняется, поэтому главные подозреваемые — аналоговый тракт захвата, который
тихо снимает питание (mic bias / ADC bias не удерживается DAPM), и underflow read-FIFO мастера
(`qcom_swrm_irq_handler: SWR read FIFO underflow fifo status 0x3` ровно в момент обрыва). Инструментировать
`dapm_widget_event` для виджетов `ADC2`/`TX SWR` и путь read-FIFO в qcom-мастере, а также попробовать
принудительно держать `MIC BIAS2` включённым через `snd_soc_dapm_force_enable_pin()`.

**Уточнение после инструментирования (отложенное чтение регистров).** Отложенное на 3 секунды чтение,
добавленное в `sdw_enable_disable_slave_ports()`, показывает состояние кодека в момент тишины: `chn_en B0 = 0x1`
сразу после записи **и через 3 секунды**, `portctl = 0x0`, `dp0_int = 0x0`, аналоговые регистры bias тоже не
меняются (`0x3023` MICB2 = `0x10`, `0x3022` MICB1 = `0x50`, `0x3001` = `0x80`). То есть TX-порт кодека включён и
исправен, mic bias поднят, прерываний нет — но сэмплы нулевые. Это снимает версию «кодек выключил свой порт» и
оставляет аналоговый выход АЦП либо путь чтения CDC-DMA в макросе.

**Предупреждение по методике (получено на практике):** не переключай маршруты FE (и вообще ничего) **при
открытом потоке**. После этого матрица ADM на ADSP остаётся в состоянии, когда появляются
`q6adm … Failed to close copp -22` и `q6asm_dai_prepare: stream reg failed ret:-22`, и тогда **пропадает и
воспроизведение**, а лечится это только перезагрузкой. Один эксперимент на загрузку, поток закрывать до любых
изменений микшера.
